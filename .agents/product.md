# Product — Otto

## Problem
- Actor / Acceptor: Windows desktop user / owner.
- Trigger: A learning question, unfamiliar concept, reading passage, diagram, writing task, or screen problem arises while the user is working or studying inside another application.
- Current behavior: Otto provides a quiet top-edge Personal AI Assistant & Learning Mentor backed by locally installed AI CLI engines, with streaming answers, local conversation history, Stop, and explicit text/screen capture. Otto is not a production coding IDE or workspace executor; installed CLI engines run under the hood using their existing auth while Otto presents a warm, non-technical assistant interface.
- Problem: Leaving the active study or reading task to ask an AI, explain a screenshot/equation/passage, get guided mentoring, or bring an answer back interrupts focus and slows learning.
- J1: When a question, study topic, or screen context arises during desktop work or learning, I want Otto to help or mentor me in place with minimal friction, so I can understand, write, and continue my task without breaking focus.

## Behavior
Primary journey: compact Agent capsule → open the Agent composer → B11 AI engine detected and ready → B21 choose a curated Learning Mode (or default) with optional static Profile & Learning Style → B9 Otto personal-assistant chat UI → B3 streaming answer with non-technical activity & optional collapsible Thinking → B8 collapse/reopen → B10 completion → B23 follow-up chips, Retry/Edit, Copy, or Insert. Settings → Assistant shows supported local CLI engines detected from PATH (with live PATH refresh) and Profile & Learning Style.
Alternate context path: trigger independent Selected Text or Visual Capture hotkey (or composer camera/paste `Ctrl+V`) → B22 stage capture/image as a composer attachment with contextual Quick Actions (or instant auto-send when enabled) → B3 answer. B7 placement applies to Agent and settings surfaces.

- B1: Otto allows only one host instance per Windows login session, then defaults to the Compact Agent capsule. Duplicate launches exit without creating another window, capturing focus, or resetting the active chat conversation.
- B2: The Agent capsule has Compact and Expanded presentations. Users can switch the Compact presentation between a `Capsule` pill (`228×40`) and an expressive `Circle` mascot (`40×40`) via a quick toggle in the Expanded header, right-click on the Compact surface, or Settings → Position; Circle mode floats automatically without erasing a saved Attached preference and reflects live Otto eye expressions (`idle`, `thinking`/`working`, `completed`, `attention`, `error`). Hover opens the Agent composer as a non-focusing preview; click/keyboard activation pins it for interaction. The Agent gear opens Settings; Otto's logo is identity only. Dismiss/Escape returns to Compact. Saved Keep Expanded governs pinned auto-collapse on desktop blur, not transient hover previews.
- B17: A global shortcut (default Ctrl+Alt+O, session-configurable) toggles Agent between Compact and pinned Expanded; Preview also toggles to Compact. It never hides the native window, exits, switches to another module, or cancels Agent work. Collapse suppresses hover reopening until pointer leave. Settings → Behavior exposes Expand on hover, Keep expanded and the shortcut under Interaction; hover timing and motion-profile controls are removed, while system reduced motion remains honored.
- B3: User chooses any installed supported local CLI engine (Codex, Pi, OpenCode, Claude Code, and compiled ACP CLIs such as Agy, Gemini CLI, Copilot, Qwen, Cursor, Goose, etc.) from the detected catalog, selects a model/thinking option via Settings or the quiet header popover when supported, asks and follows up with streaming output and Stop; the selected runtime does not own Otto conversation identity.
- B4: An explicit camera action or Visual Capture hotkey intentionally captures the configured visual source (Region Snip, last focused non-Otto window, scrolling window, or full screen) and sends or stages that image for an engine with image support.
- B20: Selected text is an explicit capture source with its own independent hotkey. While another application retains focus, the user selects text and presses the Selected Text shortcut; Otto reads only the active Windows accessibility selection, bounds and cleans it, and attaches it as untrusted non-persistent context for the active engine without clipboard access. Completed answers from any turn (chat, visual capture, or selected text) expose an explicit Insert action to send text as Unicode keyboard input to the caret in the last focused external app without using the clipboard; standalone Markdown code-fence lines are removed while line breaks and indentation remain unchanged.
- B19: Mac-native sizing is Otto's only visual sizing system, using measured Mac camera geometry when available and approximate reference proportions otherwise. Remove the legacy Default sizing option without resetting other preferences or chats. Shell corners follow notch geometry rather than pill rounding; attached retains a flat top with concave shoulders and rounded bottom corners. Agent and settings surfaces share the same shell sizing and placement behavior.
- B7: User selects floating or top-attached placement; the capsule morphs into a rounded Expanded card. The floating panel can be dragged to a custom desktop position and reset to its default centered placement. Attached uses curved shoulders connected to the screen edge; both placements preserve interaction without trapping or obscuring unrelated desktop actions. Otto requests an untitled native tool window to reduce Window source-picker listings where capture backends filter untitled or tool windows.
- B8: Collapsing Otto or returning focus to another app does not cancel an active AI request; reopening reveals ongoing output or its completed answer. Explicit Stop cancels; exiting Otto ends owned active work.
- B9: Otto acts as a Personal AI Assistant & Learning Mentor answering open-ended questions, guiding understanding, explaining concepts, helping with writing/translation, and running lightweight practice/quiz exchanges, framed with read-only assistant guidance so underlying CLIs do not perform unsolicited local file edits or commands. Otto adds no workspace picker, file-edit executor, or shell executor.
- B10: Background Agent updates never change the active surface or seize keyboard focus; completed AI work appears as a quiet 'Answer ready' status that can be opened on demand.
- B11: Engine setup exposes whether the CLI is ready, needs authentication/setup, or lacks a required capability, and supports live PATH refresh without restarting Otto; user can recover or select another engine without losing a draft.
- B12: Streaming answers render Markdown, code and math safely, support copying, and never execute model-supplied HTML.
- B13: Otto has no Coding mode, workspace/folder selector, edit executor, or shell executor. Underlying CLIs keep their native configuration; if an engine requests a host permission decision during a turn, Otto never auto-approves it and surfaces a lightweight inline choice ("Decline & continue" or "Allow once") so the session can continue safely rather than crashing.
- B14: Otto-owned conversation and history survive engine/model switching between turns; when a native session cannot resume, reconstruct only bounded saved transcript context and label the limitation.
- B21: Otto provides 6 curated fixed Learning Modes (Direct, Solve for verified math/logic/competitive programming, Mentor/Socratic, Simple/ELI5, Write & Translate, Practice/Quiz) switchable quickly via a quiet composer pill or `/slash` command, plus a non-blocking 3-step first-run onboarding and "Profile & Learning Style" section in Settings (name, role/background, focus & interests, preferred answer language, level/tone, brief static instructions) that adapts Otto's system prompt to who the user is across turns without blocking immediate chatting. UI copy stays warm, modern, non-technical English while AI answers follow the user's Profile language.
- B22: Capture and context inputs follow a staged-first composer workflow: Region Snip, Window/Scrolling/Full Screen screenshots, Selected Text, and pasted/dropped images (`Ctrl+V`) land as removable composer attachment chips accompanied by contextual Quick Actions (e.g., Explain, Break down, Translate, Summarize, Quiz me, Rewrite); pressing Enter with an empty prompt runs the default action, and an optional Settings toggle restores Instant auto-send. Selected Text and Visual Capture have independent global shortcuts, and the composer camera control lets the user pick visual capture sources without opening Settings.
- B23: Conversations retain up to 100 messages and support Retry/Regenerate, Edit prompt & re-run, preserving partial output on explicit Stop (clearly marked Stopped, never fabricated as Completed), queueing one follow-up message while streaming, 3–4 lightweight learning follow-up chips beneath the latest completed answer ("Simpler", "Give an example", "Quiz me", "Go deeper"), universal caret `Insert` on any completed answer, plus full-text History search and Markdown export.
- B24: Provider activity uses non-technical personal-assistant labels ("Thinking", "Searching", "Reading context", "Writing answer") with an optional collapsible Thinking/Reasoning block when the engine streams thoughts; persistent multi-turn sessions are reused where supported (including Codex, ACP, Pi, Claude Code stream-json, and OpenCode), per-engine readiness and model catalogs are cached in RAM and disk with stale-while-revalidate (zero subprocesses on same-engine model switching and decoupled background rate-limit fetches), active engine/model/thinking/pinned-model preferences persist across switches and restarts, one active-engine warm standby process starts on expand or engine switch with idle auto-shutdown (preserving zero CLI processes during Compact idle boot), turns render the user prompt immediately with async history persistence and leading-edge streaming plus subtle completion latency meta, a minimalist searchable/pinnable model picker and `Ctrl+M` switcher speed up selection, and CLI failures surface clear recoverable diagnostics.

Material breaks:
- X1 (B3,B11): CLI absent, incompatible, or fails → explain clearly, preserve draft/session context, offer setup, live PATH refresh, retry, or engine switch.
- X2 (B4,B22): Capture permission unavailable or active engine/model cannot take images → no image submission; show a recoverable reason and offer engine switch.
- X4 (B3,B8,B23): User explicitly stops or exits during a run → terminate owned work; preserve any already-streamed partial text marked Stopped without fabricating completion; no late response becomes current; collapse alone never triggers cancellation.
- X5 (B1,B7): User-configurable best-effort Windows capture exclusion defaults ON; a change requires native readback before the local preference is persisted. Recorders may still capture or list Otto. Never promise universal invisibility, process hiding or picker exclusion; failed settings preserve the reported native state and offer retry.
- X6 (B4): Last focused external window no longer exists or is ambiguous → do not silently capture a different target; offer user-controlled retry/selection.
- X7 (B9,B13,B24): Otto never rewrites provider-native configuration or auto-approves a host permission request. When a CLI requests host permission, Otto pauses for an explicit user decision ("Decline & continue" or "Allow once"); declining sends a graceful denial so the engine can answer in text or finish cleanly.
- X8 (B4,B22): Either independent capture hotkey (Selected Text or Visual Capture) conflicts with another shortcut or cannot register → show conflict and allow reassignment; never silently capture.
- X9 (B11): CLI exists but authentication/session expired → show setup/sign-in required; do not falsely mark it ready.
- X10 (B8): After app restart, an interrupted CLI session cannot be recovered → distinguish finished history from interrupted/unknown state, never fabricate a completed answer.
- X11 (B12): Unsafe provider HTML, links or partial Markdown → inert rendering; no model-supplied script execution.
- X12 (B13,B24): An engine sends an unsupported or malformed host request that cannot be answered via the inline permission card → decline safely or fail recoverably, preserve the conversation, and direct the user to the engine's native settings.
- X13 (B14): Switch cannot recover exact native provider context → show bounded transcript reconstruction, never claim exact native resume.
- X18 (B20,B23): No readable accessibility selection exists, the selection exceeds the bounded input, the source application denies access, or the insertion destination cannot be focused → send nothing to the provider or destination as applicable, preserve the answer, and explain how to select text or focus an editable field before retrying.
- X17 (B7,Q4): Attached placement cannot be applied or its native hit region is rejected → keep the reported placement, never paint an unconfirmed silhouette, and offer retry or the other placement.
- X19 (B22): Region snip cancelled via Escape, pasted/dropped image invalid or over size limit, or active engine cannot accept images → keep composer draft intact, discard invalid attachment cleanly, and offer engine switch or text-only continuation without sending an image.
- X20 (B23): Queued follow-up interrupted by Stop or run error, or History Markdown export fails → restore queued text to the composer draft or show a recoverable export error without losing conversation history.
- X21 (B24): Pending inline host permission request times out, is dismissed, or engine disconnects while waiting → send explicit denial/cancel if connected (never auto-approve), preserve partial transcript context, and offer Retry.


## Constraints
- C1: Windows 11 first; Tauri 2 + React + Vite + Rust + Tailwind CSS, Bun for JS package management/scripts.
- C2: 100% locally installed CLI-backed engines (Codex, Pi, OpenCode, Claude Code, and 15 compiled ACP CLIs) using their existing authentication. Detect installed supported commands from PATH (with explicit live PATH refresh); no direct model API, hosted model gateway, dynamic plugin loader, or backend service.
- C3: Low idle resource usage, responsive interface, and recoverable external dependencies.
- C4: Always-on-top and capture exclusion are best effort; secure desktop, fullscreen modes, and third-party capture paths may behave differently.
- C5: Compact dark UI with warm, non-technical English interface copy; UIArc is a visual reference, not a runtime dependency.
- C6: Screen capture, region snip, pasted/dropped image, and selected-text capture happen only after an explicit user action; do not perform periodic/automatic collection.
- C7: Otto is a Personal AI Assistant & Learning Mentor — it adds no coding workspace picker, file-edit executor, or shell executor, and does not rewrite provider CLI configuration or inject custom sandbox/deny-list flags. Prompts frame the assistant as a non-destructive mentor/helper, and any host permission request from an engine is never auto-approved: Otto mediates an explicit user choice ("Decline & continue" or "Allow once") inline.
- C8: Otto owns conversation identity, learning mode & static profile prompt framing, process lifecycle, explicit capture/attachments, and the quiet overlay UI; each CLI owns its native configuration, auth, and protocol behavior.
- Q1: Measure Windows idle CPU/memory and interaction frame pacing on a representative machine; numeric thresholds remain undefined pending baseline (A2).
- Q2: During CLI execution, users can still collapse, reopen, queue a follow-up, and stop without UI freezing; record interaction responsiveness during a real run.
- Q3: Invalid/unsupported engine, hotkey, attachment, or capture capability leaves a clear recoverable state, not a misleading success indication.
- Q4: Background activity must not unexpectedly change active view or keyboard focus.
- Q5: Screen, snip, image, or selected text must not be submitted without an explicit user action; the user can see and remove staged attachments before sending (unless Instant auto-send is opted in).
- Q6: User can obtain a helpful explanation or mentored answer and return to the original desktop task without opening a separate AI interface.

## Scope
- Agent scope: Personal AI Assistant & Learning Mentor powered by 19 compiled local CLI engines (Codex, Pi, OpenCode, Claude Code, and 15 ACP CLIs) with streaming chat, 5 curated Learning Modes (Direct, Mentor, Simple, Write & Translate, Practice), static Profile & Learning Style, quick header Engine/Model/Thinking popover, safe Markdown/math, non-technical activity trail + optional collapsible Thinking block, graceful inline host-permission choices, staged-first capture & attachments (Region Snip, Window, Scrolling, Full Screen, Selected Text, pasted/dropped images) with contextual Quick Actions and dual independent hotkeys, up to 100-message local history with full-text search & Markdown export, Retry/Edit/Queue/Stop-partial controls, post-answer learning follow-up chips, universal caret Insert, persistent Codex/OpenCode sessions, Claude/OpenCode capability parity, and live PATH refresh.
- Current product surfaces: the Agent capsule/circle/composer (with inline History view and lightweight header/camera popovers) and one Settings surface (Assistant [Engines + Profile & Learning Style], Capture, Behavior, Position, General). The Agent composer opens directly from Compact; there is no Home launcher or alternate feature module.
- Out: Production coding IDE features, workspace/folder (`cwd`) picker, diff viewer, Otto-owned file-edit/shell executor, cross-session automatic memory DB, study notebook/flashcard LMS, custom preset CRUD, direct HTTP model APIs / Ollama / cloud gateway, Home launcher, Music, Focus/Pomodoro, module carousel, Appearance customization, Otto Dock/taskbar auto-hide controls, multi-agent orchestration, dynamic plugin loader, automatic screen surveillance, speculative databases/services, and multi-OS parity.

## Assumptions
- A1 [non-blocking]: Adapter support is compiled into Otto; the installed subset is detected from PATH at runtime (and refreshed on demand via live Windows environment lookup). Engine capabilities continue to depend on each CLI version.
- A2 [non-blocking]: Hard performance budgets are deliberately undefined until Windows idle/active measurements exist.
- A3 [non-blocking]: Visual capture defaults to the user's chosen visual source (Region Snip, last focused external window, scrolling window, or full screen), selectable directly from the composer camera menu or Capture settings.
- A4 [non-blocking]: Otto has no owned tool executor. Underlying CLIs remain external processes; Otto frames prompts for non-destructive personal assistance and mediates any host permission prompt explicitly without auto-approval.
- A5 [non-blocking]: Otto owns local text conversation history (up to 100 messages per conversation); provider thread IDs, credentials, pasted/captured images, and selected text are not persisted in History. Reopen reconstructs bounded context from the local transcript.
- A6 [non-blocking]: Cross-engine continuation retains Otto text history and uses a native session only when the active adapter supports it; real provider follow-up, Claude/OpenCode image/model flags, and process cleanup still need Windows acceptance.
- A8 [non-blocking]: PATH detection only reports supported adapters already compiled into Otto; adding a new CLI requires an adapter change, not a user-installed plugin.
- A9 [non-blocking]: Provider-native capabilities (such as web search or tools configured natively inside a CLI) depend on each CLI's own settings; Otto never silently elevates permissions or hides host permission decisions.
- A10 [non-blocking]: Selected-text capture depends on the source application's Windows UI Automation TextPattern support; unsupported controls remain a recoverable native limitation rather than falling back to clipboard or document scraping.
- A11 [non-blocking]: Native Windows Region Snip overlay selection, multi-DPI coordinate mapping, dual independent hotkey conflict handling, and live Windows registry PATH refresh require representative Windows acceptance.
